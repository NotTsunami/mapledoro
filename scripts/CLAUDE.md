# Data Generators

Everything in `scripts/` writes generated data into the app (`public/data/`, `*.generated.ts`, `*Data.ts`). Nothing here runs at build time, so a stale output never errors, it just serves old content: re-run the generator and diff its output before committing.

Two triggers, one per group below: a game version bump for the manifest generators, and the source's own changes for the scrapers.

## Manifest generators (version bump)

- **Bumping the version:** every `gen-*.mjs`/`generate-*.mjs` has its own hardcoded manifest path. Grep `scripts/` for the old version string and update every hit together, or a generator silently keeps reading the old manifest and masks real data drift.
- **After bumping, actually re-run each generator** — repointing isn't regenerating. At minimum: `gen-equipment.mjs` (needs `EQUIP_ICON_DIR` + `EQUIP_DEDUP_VERDICTS`, see its doc comment), `gen-familiars.mjs` (needs `FAMILIAR_DUMP_DIR` for reissue dedup; without it, duplicate picker rows return), `gen-familiar-traits.mjs` (Mystic Frontier joins its output with `gen-familiars.mjs`'s by id, so run both), `gen-mf-potentials.mjs` (a new condition wording also needs a matcher in `potentialEngine.ts` or the line never scores), `gen-vmatrix.mjs`, `gen-stat-baselines.mjs`. Diff before committing; a same-id-count regen can still hide real stat/name changes.
- **The daily games' generators are excluded** — regenerating a puzzle payload reshuffles the daily order and breaks in-flight streaks, so a version bump is not a reason to re-run them (Mapledle's payload is still v269 on purpose; see its feature doc).

## External data scrapers (own trigger)

These read live external sites rather than WZ manifests, so a version bump is not their trigger.

- `generate-bgm-guesser-data.mjs` → `src/features/games/bgm-guesser/puzzle-data.generated.ts`. Combines `manifests/v270/bgm.json` (its `MANIFEST_VERSION`, pinned on purpose) with a hand-curated track→answer allowlist in the script, fetching [maplebgm-db](https://github.com/maplestory-music/maplebgm-db) at generation time for titles. Re-run only when the curation changes; it exits non-zero if a curated track or answer icon no longer resolves. New BGMs are *not* picked up automatically, by design.
- `scrape-bosscut.mjs` → `src/features/characters/scouter/bosscut-data.generated.ts`. MapleScouter's crowdsourced Boss Clear (Cut) thresholds and boss requirement physics. Re-run whenever a MapleStory version drops: MapleScouter adds new bosses ahead of the official patch, so this both picks up new content and re-syncs community-revised numbers. It locates the data by content-fingerprinting its object shape, not a module ID or chunk filename (both reshuffle every deploy). A failed fingerprint, or output that stops matching real in-game results, means the data shape or the formula itself changed — investigate before trusting it.
- `scrape-lowend-bosses.mjs` → `src/features/characters/scouter/lowend-boss-data.generated.ts`. Boss Clear entries for the bosses MapleScouter has no cut for (Zakum through Akechi), estimated from boss HP, defense and time limit on the MapleStory Wiki (`?action=raw` page source, about 40 requests 3 seconds apart). The HP-to-cut constant is re-derived each run from MapleScouter's own older bosses, so re-run it after `scrape-bosscut.mjs` or a patch that changes boss HP. It exits if too few reference bosses match, which means a wiki page or the scraped cut data changed shape.
- `calibrate-scouter.mjs` (report only; a class whose factor is consistent gets it copied by hand into `src/features/characters/scouter/engine/classClearFactors.ts`). Compares MapleScouter's Boss Clear % against real clears logged by hand in a separate dataset outside the repo (`--clears <file>`; its video links identify players), per class and per class+boss, with KMS classes as the ~1.0 control group. `probe` mode fetches each class's spline and constants once into `class-probes.json`; a clear then needs just its HEXA value. Probing calls MapleScouter, which blocks hosting providers, so run it from a home connection. Re-probe (`probe <ids...>`) after MapleScouter changes a class's numbers, and re-run the report after `scrape-bosscut.mjs`.
- `scouter-calibration/build-engine-data.mjs` → `public/data/scouter-engine.json`, the per-class constants the app's local Scouter engine (`src/features/characters/scouter/engine/scouterEngine.ts`) runs on. See "Scouter engine: after a patch" below.
- `scrape-class-resources.mjs` → `src/app/guides/character-guides/classResources.ts` (used by the `[className]` guide page). Per-class community links from a third-party class-reference site (URL in the script). Re-run only when a class's resources change or a new class needs an entry, not on a version bump; its `CLASS_PATHS` table maps our class names to that source's slugs.

## Scouter engine: after a patch

The Scouter figures, Boss Clear inputs and Stat Efficiency all come from a local rebuild of MapleScouter's damage calculation, running on per-class constants in `public/data/scouter-engine.json`. Those constants were derived from MapleScouter probes, so re-check them when GMS or KMS patches, or when MapleScouter says it changed a class.

Every script below takes `--data <dir>`: the raw probes and the reference sheet they were all measured from (a real character's sheet). Keep that folder private and never commit it. The scripts call MapleScouter: run them from a home connection, send at most 50 requests, then wait 10 minutes, and stop at the first error. If MapleScouter blocks scripted requests (it started answering 401 "humanToken missing" in October 2026), none of this can run; never work around a block.

1. **Check for drift:** `node scripts/scouter-calibration/drift-check.mjs --data <dir>` (53 requests, so two runs). It lists every class whose damage, HEXA or HEXA curves moved. Nothing moved means you're done.
2. **Re-measure what moved.** If only a class's curves moved, `node scripts/calibrate-scouter.mjs probe --data <dir> <classId>` is enough. Otherwise run `sweep.mjs --data <dir> <classId> --set all --into fresh.json` (80 to 330 requests per class, over several runs), then `sweep.mjs --data <dir> <classId...> --adopt fresh.json`.
3. **Rebuild and check:** `build-engine-data.mjs --data <dir>`, then `validate.mjs --data <dir> --recheck` (re-sends the 159 test sheets and flags any answer that changed), then `validate.mjs --data <dir> --max 0` for the summary. Compare it with the last good run: median damage error about 0.02%, 100 of 159 sheets within 10 HEXA.
4. **Commit `public/data/scouter-engine.json`.** Players get the new numbers on their next visit, since results are recomputed from current data every time.

A class's HEXA skills reworked in a patch can also change the stepped HEXA patterns listed in `CORE_STEPS` (`scouterEngine.ts`), which come from the MapleStory Wiki's per-level skill tables. Re-read that class's table. A new class needs the full probe set (`sweep.mjs` with each `--set` in turn, roughly 300 requests) plus its `scouterClassNames.ts` entry.
